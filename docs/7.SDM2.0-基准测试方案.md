# SDM2.0 基准测试方案

> **目标：** 对 S0、S1、S2、S3 四种存储模型进行可重复、可解释的对比。测试不仅验证数据生成、写入和查询命中，还评估上层 SOC 业务调用的实现复杂度与运行成本。
>
> **业务依据：** 测试场景来源于 `4.SDM2.0-日志模型概念研究.md` 和 `5.SDM2.0-日志模型调查视图补充.md`。

## 一、测试阶段

| 阶段 | 目标 | 主要产物 |
|------|------|----------|
| T0 数据生成 | 生成相同语义、相同时间范围的 S0/S1/S2/S3 数据 | `_summary.json`、`query_params.json`、分层 JSONL |
| T1 建表与写入 | 验证 55 张表可创建、全量数据可加载 | DDL summary、load report |
| T2 数据完整性 | 验证计划行数与 Doris 实际行数一致 | per-table count validation |
| T3 查询命中 | 验证高频、低频和实体参数可命中 | hit-validation report |
| T4 业务调用复杂度 | 比较相同业务场景在四种模型上的实现和运行成本 | workload manifest、SQL、complexity report |
| T5 规模性能 | 在 smoke、pilot 和正式规模下比较延迟与资源消耗 | latency/profile report |

完整验收至少执行 T0-T4。T5 用于容量规划和最终模型选型，不替代前面的正确性验收。

T4 首版实现位于 `benchmark/query/`，覆盖 B01-B08。执行入口：

```bash
python3 benchmark/query/sdm2_business_query_benchmark.py \
  --dataset-root benchmark/reports/converted/smoke \
  --scenarios B01,B02,B03,B04,B05,B06,B07,B08 \
  --schemes s0,s1,s2,s3
```

使用 `--dry-run` 时只输出脱敏计划和渲染 SQL，不连接 Doris，也不写报告。

## 二、业务场景工作负载

每个场景必须定义相同的业务输入、时间范围、排序、分页和期望结果语义，再分别提供 S0、S1、S2、S3 实现。不得为了某个模型简化业务语义。

### 2.1 第一阶段：现有字段可完整支持

| ID | 业务入口 | 查询条件 | 业务问题 | 期望输出 |
|----|----------|----------|----------|----------|
| B01 | SOC 事件列表筛选 | 租户、时间范围、事件类型、严重级别 | 值班人员筛选某类高危事件，快速定位优先处理对象 | `sdm_fieldset.core` 字段、倒序分页 |
| B02 | IP 调查 / 源 IP 透视 | 租户、时间范围、源 IP | 查看可疑源 IP 访问过哪些目标、端口、协议和域名 | `sdm_fieldset.network` 当前可用字段 |
| B03 | 同类告警排查 | 租户、时间范围、来源告警严重级别、来源告警名称 | 追查同类告警是否批量出现，并查看来源产品和原始日志引用 | 事件摘要、来源告警、原始日志引用 |
| B04 | IP 实体画像 / 实体时间线 | 租户、时间范围、IP 实体；S0/S1/S2 等价展开 source/target IP | 查看一个 IP 什么时候作为源或目标参与事件 | 按时间排序的事件及角色 |
| B05 | 用户实体画像 / 用户时间线 | 租户、时间范围、源用户名 | 查看账号在调查时间窗内参与过哪些事件和主机活动 | 用户参与的事件及角色 |
| B06 | 实体关系扩展 | 租户、时间范围、起始 IP 实体、结果上限 | 从可疑实体展开相邻实体、关系角色和证据事件 | 相邻实体、关系角色、证据事件 |
| B07 | 原始日志回溯 | 租户、共享 `log_id`，可选 `event_id` | 从标准化事件回溯到原始日志引用，支持证据复核 | `raw_log_ref` 和来源信息 |
| B08 | 调查聚合 / 事件类型分布 | 租户、时间范围、源 IP | 汇总可疑源 IP 的事件类型分布和首次、末次出现时间 | 次数、首次/末次出现、Top N |

### 2.2 第二阶段：需要调查故事数据集

| ID | 业务场景 | 需要补充的数据 |
|----|----------|----------------|
| B09 | 端点调查视图 | 统一进程 GUID、父进程 GUID、命令行、文件 Hash |
| B10 | 身份认证调查视图 | 用户类型、目标服务、认证结果、设备标识 |
| B11 | 进程生命周期 | PROCESS_LAUNCH/NETWORK/FILE/TERMINATE 串联事件 |
| B12 | 行为链还原 | AUTH_LOGIN→PROCESS_LAUNCH→DNS→HTTP→FILE→DETECTION |

第二阶段数据必须通过固定 seed 和显式故事模板生成。禁止在查询 SQL 中硬编码不存在的关联关系。

## 三、模型等价实现要求

| 模型 | 查询实现基线 |
|------|--------------|
| S0 多表 | 使用相关 LDM 表的 `UNION ALL`，保留厂商字段适配和标准字段投影 |
| S1 VARIANT | 从 `sdm_log_variant` 的标准列和 VARIANT 路径提取业务字段 |
| S2 宽表 | 从 `sdm_event` 完成事件筛选、展示和必要的自关联 |
| S3 语义表 | 使用 `sdm_event`、`sdm_event_role`、`sdm_entity_activity` 完成事件与实体查询 |

每个实现必须返回统一列名和数据类型，并通过结果一致性校验：

- 主键或业务标识集合一致。
- 行数一致；允许的重复消除规则需在 workload 中声明。
- 时间排序和分页边界一致。
- 展示字段缺失必须显式记为字段覆盖率问题，不得用空常量掩盖。
- 模型语义不适用字段必须显式记为 `not_applicable_fields`，例如 S0/S1 的 `event_id`；这类字段不计入字段覆盖率扣分。

## 四、复杂度与性能指标

### 4.1 调用复杂度

| 指标 | 定义 |
|------|------|
| `statement_count` | 完成一次业务调用所需 SQL 次数 |
| `table_count` | 查询涉及的物理表数量 |
| `union_count` | `UNION/UNION ALL` 数量 |
| `join_count` | JOIN 数量 |
| `json_path_count` | VARIANT/JSON 路径引用数量 |
| `projection_count` | 输出字段及兼容投影数量 |
| `vendor_branch_count` | 厂商或日志类型条件分支数量 |
| `sql_lines` | 去除空行和注释后的 SQL 行数 |
| `post_process_steps` | 应用层合并、去重、补字段、二次查询步骤数 |

复杂度报告必须保留原始计数，不只输出单一综合分。可额外提供加权分数用于排序，但权重必须记录在报告中。

### 4.2 字段与结果质量

- fieldset 字段覆盖率。
- 非空字段覆盖率。
- 结果集合一致率。
- 实体标识可归并率。
- 原始日志可回溯率。
- 行为链预期步骤召回率。

### 4.3 运行复杂度

- 冷运行和热运行的 p50、p95、最大延迟。
- 返回行数、扫描行数、扫描字节数。
- CPU 时间、峰值内存和 Query Profile。
- 分区裁剪、索引命中和物化结果复用情况。
- 客户端请求次数及传输字节数。

性能测试应至少预热 3 次、测量 10 次。各模型应使用相同参数和并发度，报告 Doris 版本、节点配置、数据规模及冷热状态。

T4 首版只采集预热后的 p50、p95、最大延迟和返回行数。扫描行数、扫描字节、CPU、峰值内存和 Query Profile 留到 T5。

## 五、执行顺序

1. 使用固定任务配置生成同一数据集。
2. 创建空数据库或 truncate 目标表。
3. 执行 `--scheme all` 写入并完成全表行数对账。
4. 运行现有 hit validator，确认参数可命中。
5. 对每个业务场景先执行结果一致性检查。
6. 一致性通过后采集静态复杂度和运行指标。
7. 按场景输出 S0-S3 横向比较，不跨场景直接合并延迟。
8. 对不支持的场景记录具体缺失字段或关联标识，不将其记为查询失败。

## 六、报告格式

每次运行至少输出以下内容：

```text
dataset / rows / time range
Doris version / topology / node resources
scenario_id / scheme / parameter set
correctness_status / result_count / field_coverage
missing_fields / not_applicable_fields
statement_count / table_count / union_count / join_count
json_path_count / vendor_branch_count / sql_lines
p50_ms / p95_ms / scanned_rows / scanned_bytes
cpu_ms / peak_memory_bytes / profile_reference
unsupported_reason / first_failure
```

推荐汇总视图：

| 场景 | 模型 | 正确性 | 字段覆盖率 | 调用复杂度 | p95 | 扫描量 | 备注 |
|------|------|--------|------------|------------|-----|--------|------|
| B04 IP 时间线 | S0 | pass | 70% | 高 | - | - | 多表 UNION |
| B04 IP 时间线 | S1 | pass | 85% | 中 | - | - | VARIANT 提取 |
| B04 IP 时间线 | S2 | pass | 85% | 中 | - | - | source/target 条件 |
| B04 IP 时间线 | S3 | pass | 100% | 低 | - | - | entity_activity |

## 七、验收标准

- T0-T3 全部通过后才允许执行复杂度和性能比较。
- 第一阶段 B01-B08 每个场景至少有 S0-S3 四份等价实现或明确的 unsupported 证据。
- 所有参与性能排名的实现必须先通过结果一致性校验。
- 报告必须同时呈现原始复杂度指标、运行指标和字段覆盖率。
- 选型结论需按业务场景给出，不以单条简单过滤查询代替整体业务复杂度。
- B09-B12 在调查故事数据集完成前仅记录为待测，不纳入最终模型优劣结论。
