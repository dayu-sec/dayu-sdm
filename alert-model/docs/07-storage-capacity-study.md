# SDM Doris 存储容量研究：CK 大禹对照实测（2026-08-24）

> 结论先行：**同数据量、同冗余度下，SDM 全量五层信封 + 全套倒排 ≈ 0.9× CK 现状存储成本**。
> 容量规划线：全量五层双副本 **~0.6 TB/周**；7 天 TTL 稳态 ~600 GiB；全年保留 ~31 TB。
> 实验产物：`output/doris_scale_test_100k/`（转换 JSONL + report.json）；测试表 `sdm2_log.t100k_{evt,raw}_{idx,noidx}`。

## 1. 背景与问题

- 数据源量级：民航局侧 ALERT_LOG ~46-83 万/天，TRAFFIC_LOG ~1.25-2.5 亿/天（采集口径）。
- 存量平台：ClickHouse（大禹），`dwd_dayu_log_*` 宽表，含 `raw_msg` 原文（非空率 100%）、WEB 表另含 `http_req_body/rsp_body/header`。
- 待答问题：SDM 五层信封模型（事件+原文两表）入 Doris，容量是 CK 的多少倍？

## 2. CK 侧实测画像（用户提供 + 交叉验证）

### 2.1 部署与占用

| 口径 | 近 7 天 | 全库 |
|---|---|---|
| 逻辑数据（单实例一份） | ~330 GiB | ~362 GiB |
| 物理占用（8123/8124 双实例各持全量） | **~667 GiB** | ~725 GiB |

- 双实例（29010/29011）数据几乎完全一致 → 双实例冗余/读写分离部署，存储数学等价 2 副本。
- `du` 6 盘 ckk 合计 727 GiB ≈ 725 + system，闭环验证。
- 保留窗口约 7 天（近 7 天占全库 91%）。

### 2.2 flow_web 单行解剖（117,271,352 行）

| 指标 | B/行 |
|---|---|
| bytes_on_disk（含索引/标记） | **2,292** |
| compressed（纯数据） | 1,413 |
| uncompressed（展开） | 12,009 |
| TSV 文本导出 | ~3,980 |

存储构成（压缩后占比）：`_all` 物化全字段 JSON **39%**（全文检索用，等于重复存全部字段）、`raw_msg` 32%、body/header 类 ~15%。**CK 为全文检索付出的代价 = `_all` 冗余 39%。**

### 2.3 行数口径（关键陷阱）

| 口径 | WEB 行/天 | 周行数 |
|---|---|---|
| 大禹日统计（采集量） | ~57M | ~400M（全类型合计 10.9 亿） |
| CK dwd 实际入库（聚合后会话） | ~17M（峰 27.8M，周末 11.2M） | **116M** |

**采集量 → 会话聚合比 ≈ 3.4×**。任何容量估算必须先确认行数口径，否则整体偏差 3.4×。

## 3. Doris SDM 侧 100k 对照实验

### 3.1 设计

- 数据：CK `flow_web` 导出 10 万行（5 天跨度，raw_msg 均 2,090B，http_req_body 50.7% 非空、非空均 266B）。
- 转换：TSV 列直取 → 五层信封（activity/network_http），raw_msg **原样**入 raw_log，body 入 `facets.http.request_body`。
- 4 张对照表（2×2 分离变量：信封/原文 × 有/无倒排），500 行/批装载，共 1,656s。
- DDL：与现网 `sdm_event`/`raw_log` 同构（UNIQUE KEY(tenant,occur_time,event_id) 按天分区；注意 SHOW CREATE 吐出的内联 `variant<PROPERTIES>` 建表不收，需剥成裸 `variant`）。

### 3.2 结果（B/行·单副本）

| 表 | 存储 | 单行 | 说明 |
|---|---|---|---|
| `t100k_evt_noidx` | 32.2 MB | **322** | 信封裸数据：JSON 2,281B → 322B（**7.1× 压缩**） |
| `t100k_evt_idx` | 45.2 MB | 452 | +10 热列倒排 = **+40%** |
| `t100k_raw_noidx` | 61.1 MB | **611** | raw_msg 2,090B → 611B（3.4×，含 digest 倒排） |
| `t100k_raw_idx` | 125.4 MB | 1,254 | +**raw_msg 全文倒排 +643B（比数据本身还贵）** |

### 3.3 同源对齐（同一批 10 万行）

| 口径 | CK | SDM | 比值 |
|---|---|---|---|
| 纯数据（各自去掉全文检索机制） | ~862 B（1,413 去 `_all` 39%） | 933 B（无倒排） | **1.08× 平价** |
| 完整磁盘占用（含索引/标记） | 2,292 B | 1,706 B（全套倒排） | **0.74×，SDM 省 26%** |

机制对照：CK 全文检索靠 `_all` 物化重复（39%），SDM 靠 raw_msg 倒排（+643B/行）——等价功能、不同实现，倒排更便宜。

## 4. 最终容量结论

### 4.1 周用量（同口径物理占用，双份冗余）

| 方案 | 周物理占用 | 备注 |
|---|---|---|
| CK 现状（双实例） | **~667 GiB** | 实测 |
| SDM 全量五层+全套倒排，2 副本 | **~600 GiB**（WEB 178 + DNS 119 + 告警 5，×2） | WEB 实测锚定；DNS 551B/行为产物外推（唯一 ± 项） |
| 同上，砍 raw_msg 全文倒排（留 digest） | ~420 GiB | 省 ~30% |
| 单机 1 副本（上游可重灌） | ~300 GiB | Doris 单 BE 强制副本数=1 |

### 4.2 保留窗口

- 7 天 TTL 稳态：~600 GiB（2 副本）
- 90 天：~2.6 TB
- 全年：~31 TB

### 4.3 成本结构（两边对称）

| | 为全文检索付的钱 | 可省幅度 |
|---|---|---|
| CK | `_all` 物化列 | -39%/单份 |
| SDM | raw_msg 倒排 | -30% |

砍不砍是需求决策（要不要原文全文检索），不是技术决策。

## 5. 估算纠偏记录（方法论存档）

本次结论经历三次修正，错误链条值得留档：

| 版本 | 结论 | 错误根源 |
|---|---|---|
| v1 | SDM 单副本 0.6-1.1 TB/周，"信封+raw 双份存储是最大头" | ① POC 4 万行小批量（27 行/tablet）碎片化把单行高估 ~2×；② 误以为 CK 不存原文 |
| v2 | SDM 全索引 5.3× CK | CK 锚点算错：把 240GiB 除以臆估 4 亿行得 323B/行；实际表 1.17 亿行，正确锚 2,292B/行 |
| v3 | 周 1.2-1.5 TB（单副本全索引） | 行数口径错：把采集量 10.9 亿/周当入库量；实际聚合后 ~3 亿/周（3.4× 高估） |
| **终版** | **SDM ≈ 0.9× CK，周双副本 ~0.6 TB** | 全部口径实测锚定 |

教训：容量估算先钉死三件事——**单行实测（大批量、compaction 后）、行数口径（采集 vs 入库）、冗余口径（逻辑 vs 物理）**。

## 6. 附：单机副本说明

- Doris 同一 tablet 多副本必须落不同 BE，单 BE 建表副本>1 直接报错；单机 = 强制 1 副本。
- 副本只防 BE 节点级故障，不防掉电/误删/磁盘坏（tablet 不跨盘冗余）。
- SDM 数据是派生数据（上游大禹/CK 可重灌），单机 1 副本 + 可选快照导出是合理选择；扩到多节点后直接上 3 副本（2 副本是写 quorum 尴尬值：再挂一台即整表只读）。
