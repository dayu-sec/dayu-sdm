Derivation

模型推导：从最低约束到六个落位

不从现有字段表开始归纳，而从「安全事件如何发生、如何被观察、如何被记录」的最低约束出发，逐步推导出逻辑模型。 事件本身没有 source / target 标签——它们是观察者对参与者在当前行为中所扮演角色的结构化表达； 原始日志也只是来源设备在特定位置、时刻与能力边界下的有限观测或声明。 推导只说明这是合理且必要的最小分解，不宣称唯一正确。

#不可绕开的问题推导结果缺少它会怎样（反事实）
1一条事件如何被唯一定位、回查和重放？元数据 = 身份 + 时间 + 来源 + 版本 + 映射契约无法判断何时、何处、由哪条映射生成，也无法对账
2这究竟是什么事件？事件 = 种类 + 领域 + 类型 + 动作 + 结果 + 严重度数据只能按厂商字段查询，无法跨来源比较
3谁通过什么，对谁做了什么？角色 = 发起方 + 载体 + 被作用方 + 关联实体 + 观测者IP、主机、账号与进程被固化为攻击者 / 受害者字段，方向反转时语义失真
4行为究竟怎么发生？行为维度 = 网络与流量 + Web 与解析 + 认证 + 进程 + …领域细节被塞进顶层或厂商私有区，公共模型持续膨胀
5哪些是观察到的事实，哪些是来源做出的判断？检测声明 = 声明者 + 判断内容 + 规则 / 证据 + 攻防声明设备的「检测到攻击」会被写成已确认的客观事实，误报污染下游研判
6标准尚未理解或不适合公共化的信息放哪？扩展区 = 私有扩展 + 资产画像 + 富化 + 未映射只能丢数据，或为每个厂商不断扩张公共 Schema
六个问题，收束为一条事件
这六个区不是字段分组的结果，而是六个无法省略的问题各自得到了一个稳定落位——下一节看它们如何组成一条事件。

推导之后得到的三条设计后果

后果 01

声明与事实分离

世界发生的事，和某人对这件事的说法，是两回事。设备说「检测到攻击」不等于攻击发生过——把说法当事实，误报就污染研判。标准让两者各居其位、互不改写，真伪留给下游判定。

落点：检测结论入 source_finding，行为事实入 roles / facets，两区各写各的。

后果 02

观测角色 ≠ 攻防角色

看见谁发起、落在谁身上，是观察；认定谁是攻击者、谁是受害者，是判断。观察可以对任何日志做，判断必须有依据——混淆两者，等于让设备的猜测冒充现场。

落点：source / target 只表达观测方向；attacker / victim 仅在源告警明确声明时构造。

后果 03

同一语义，只有一个标准落位

落位一旦重复，映射无从评审、查询无从预期——标准开始失效。

落点：同一实体建一次、他以 ref_id 引用；装不下的进 extensions 受治理，不另立标准位。

Derived Structure

推导结果：六区组成一条事件

六个问题已经得到六个落位，现在看它们如何组成一条事件；每区一句职责。 如何存储落表属于物理绑定，见手册 · 物理投影。 

SDM Event = metadata + event + roles + facets + source_finding + extensions
metadataMETADATA –字段 接入来源、时间、标识和治理信息：租户、event_id、mapping_id、来源厂商 / 产品 / 实例、原始日志编号；原文独立保存，经 event_id 1:1 回查。
eventEVENT –字段 事件种类、领域、行为、结果和严重度：record_kind、event_domain、event_type、operation、outcome、severity。
rolesROLES –字段 谁 通过什么 对谁 做了什么 + 关联实体：source、carriers[]、target、related[]、observer 五类观测角色。
facetsFACETS –字段 行为怎么发生的细节维度：network、http、dns、email、file_activity、process、authentication、registry、application、container。
source_findingDECLARATION –字段 设备怎么认定的（告警声明）：标题、等级、分类、规则、ATT&CK、攻防双方、指标与漏洞、处置与判定结论。
extensionsEXTENSION 19Profile 路径 装不下的才进扩展区：source_private（私有扩展）、profiles（资产画像）、enrichments（富化）、unmapped（未映射）。
Event Layer

事件层：这是什么事件、结果如何

顶层六个字段回答第一问「这是什么」：种类（record_kind）、领域（domain）、类型与动作（type × operation）、结果（outcome）、严重度（severity）。 知道是什么，再看「谁对谁」。

字段取值判别
record_kindactivity / finding / inventory / state / remediation按日志内容性质判别，不看设备类型：finding = 来源设备的检测声明，真假由下游研判
event_domainidentity / network / endpoint / threat / asset / system / application / discovery（开放推荐值）事件领域；与 metadata.data_source.category 的分工见元数据扩展区
event.type × operation105 项受控字典未登记组合的 operation 必须留空；已废弃类型只读兼容。查字典 →
outcomesuccess / failed / observed / denied / allowed / unknown视角决定词表：存在访问控制 / 策略判定 → 站被判定方（denied / allowed）；纯行为记录 → 站行为主体（success / failed / observed / unknown）
severitysyslog 八级 emerg → debug与来源告警高 / 中 / 低危分轨：后者写 source_finding.severity，不机械投影
易错对照

登录被拒 = denied 不是 failed

认证是控制点判定，站被判定方；端口连不通无守门人，是行为本身 failed；流量镜像只是观察到，记 observed。

一致性约束

denied 必有声明同面

denied / allowed 几乎必然伴随 source_finding.action（block / allow）——同一事实的两面；写了 denied 却无 action 声明，视为映射缺陷。

来源 blocked

按语义归一为 denied

event.outcome 不保存阻断动作字面量：来源写 blocked 一律按语义归一为 denied，词表保持六值闭合。

Roles · Subject & Object

角色区：谁通过什么对谁

行为句式 = 主体（source）通过工具（carriers）作用于客体（target）。 这是人类语言对事件的基本编码（主谓宾 / 施事-受事-工具），也是 RDF 三元组的形状。 谁对谁清楚了，下一节看「怎么发生的」。

观测角色主客体可放对象要点
source 发起方行为主体 · 施事host、process、user、account、endpoint、geo、resource观测到的发起方，不自动等于攻击者
carriers[] 载体工具 · 载体process、script、resource行为链主载体；多级工具链按序排列
target 被作用方行为客体 · 受事host、process、file、user、account、domain、url、endpoint、service、geo、resource观测到的被作用方，不自动等于受害者
related[]其他参与者上述对象皆可带 relation_type（父进程、关联主机…）
observer观测者product、device、resource采集或观察事件的产品与设备
两层主客体 · 观察

roles 只写看出来的

连接方向、进程父子关系是观察事实：source / target 表达观测方向，任何 log_type 都能填。

两层主客体 · 声明

攻防只写判出来的

attacker / victim 仅在源告警明确声明时在 source_finding 中构造。端口扫描里 source=attacker；C2 外联里 source=受害机=victim——方向相反也存不错。

对象去重

ref_id 关联

同一实体只建一个主对象，其他位置用 ref_id（如 process::xxx）关联，不在多个角色下重复构造。

Facets

行为维度区：怎么发生的

行为细节按维度拆放：注册 – 个 domain，当前 504 条路径启用 – 个，页面按主题组展开； 全量字段见手册 · 字段目录。如果这条日志是设备检测出来的，判断放哪？下一节回答。

Declaration · source_finding

告警声明区：设备怎么认定的

source_finding 回答「设备怎么认定的」。 一条被判定为攻击的行为日志，roles 里只有观测到的 source 与 target——声明不改写事实。 最后两块：事件的身份证，和装不下的字段。

source_finding · 八组声明字段

分组内容
基本属性title、description、severity、status、count、confidence
分类category（original + normalized 两级）、original_category
检测rule / rules[]、detection_method、protection
攻击框架mitre（technique_id、tactics、techniques）、killchain
攻防双方attacker / victim / entities[] — 仅源告警明确声明时构造
指标与漏洞indicators[]、ioc、malware、vulnerability、weak_password
处置与证据remediation、evidence、attention、window、duration
判定结论attack_direction、attack_result、compromise_status
record_kind

finding 是声明

record_kind=finding 表示来源设备的检测记录；activity 是行为活动。声明真假由下游研判，不在日志层判定。

severity 分轨

两套严重度不混用

event.severity 用 syslog 八级；来源告警的高 / 中 / 低危写 source_finding.severity，不机械投影。

声明即检出入口

声明 → 检出

设备检测声明保存在 source_finding；来源告警接入路径把它作为平台告警 SOURCE_ALERT 的事实来源，完整机制见 alert-model 文档。

Metadata & Extensions

元数据与扩展区：身份证与装不下的字段

metadata 给事件发身份证，extensions 收编装不下的字段——模型到此定型，接下来看真实日志怎么进来。

身份

两列身份

event_id 是标准化事件唯一标识（平台分配，与 raw_log 1:1）；log_id 是原始日志身份——来源有稳定 ID 填来源 ID，否则与 event_id 相同。

时间

三戳 · Unix 毫秒

时间统一 Unix 毫秒 UTC：occur_time 事件发生、ingest_time 接入、parse_time 解析。

治理

mapping_id · schema_version

每条事件携带映射契约编号与逻辑模型版本，管道全程不丢；中间版本暂不承载 mapping_revision 等治理字段。

extensions 容器收什么
source_private来源私有扩展：标准字典之外但结构稳定的厂商字段
profiles资产画像：endpoint_asset 等 19 条 Profile 路径，由 Profile registry v2 单独治理
enrichments富化：IP 地理 / 资产 / 系统 / 组织 / 方向等接入侧补充
unmapped未映射：暂无标准落位的字段，受治理、可统计，映射状态区分完整 / 部分 / 未映射
超限

overflow 引用

对象超 inline 上限时写 overflow:// 引用并标 overflow_reference；单对象上限 16 / 32 / 32 / 64 KiB（四个对象区），合计 128 KiB。

数据来源类别

data_src_category 六值

auth / network / audit / system / alert / other，按日志内容性质判别（非设备类型）：防火墙攻击告警 = alert，纯流量 = network；同一产品不同 log_type 可落不同值。

索引策略

V3 倒排承接低频路径

roles_obj / facets_obj / source_finding_obj 建倒排索引承接低频标量路径过滤；extensions_obj 不建无约束全路径索引；数组任意成员查询不依赖下标方案。

13 个降级路径

低频投影退回对象

已通过 Doris 路径查询验证的 13 个低频标量投影降级到 roles_obj / facets_obj 权威存储，逻辑路径保留、物理列不建。

一致性要求 · 写入端必须保证
  1. 同源 — 标量投影来源于本条消息的权威逻辑对象，不能由另一套独立映射产生。
  2. DIRECT 相等 — 单值 DIRECT 投影必须与对象值相等。
  3. 可复现 — NORMALIZED / DERIVED 投影必须能按注册规则从对象值复现。
  4. 主值稳定 — PRIMARY_ONLY 必须使用注册的主值选择规则，不依赖数组偶然顺序。
  5. 不凭空造值 — 对象值缺失时不生成对应标量投影；补充值必须同时带允许的富化来源。

idx_raw_msgINVERTED原文全文检索（unicode parser）

同构身份 · 与 sdm_event

UNIQUE KEY 三列一致

tenant_id + occur_time + event_id 唯一键、HASH 分布与日分区策略与 sdm_event 同构；同一 event_id 重灌时两表 upsert 行为一致。

同文判定

digest 双列

WHERE digest_algo = ? AND raw_msg_digest = ? 判定原文是否同文；digest 由上游 wparse 计算后随消息写入，027 落库不重算。

索引与保留

双倒排 + Bloom

raw_msg 全文倒排、raw_msg_digest 倒排；event_id / raw_msg_digest 建 Bloom 过滤。保留期由 apply 脚本按 DORIS_RETENTION_DAYS 替换（默认 7 天）。

独立原文表契约 · 006_raw_log.sql
raw_log 的唯一机器依据：6 列 + 2 倒排索引；事件表只存 event_id 引用，原文不参与字段映射。
